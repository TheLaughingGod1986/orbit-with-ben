# Field Order History analytics

J3006 builds the read-only API collection and board card before channel creation. It is disabled unless both `YT_CHANNEL_ID_WW2` and `YT_ANALYTICS_REFRESH_TOKEN_WW2` are set locally. There is no fallback to another channel's Analytics login. No credentials, account addresses or private network details belong here.

To activate after the channel exists, configure its public channel ID locally in `07_Content-Ops/.env`, then Ben runs `npx tsx --env-file=.env scripts/youtube-auth.ts --analytics ww2` from `07_Content-Ops`. This requests only `youtube.readonly` and `yt-analytics.readonly`, verifies the selected channel and preserves the upload login. Do not start the sign-in unattended. The existing 06:40 snapshot job then includes this channel and commits this directory; an explicit `analytics:snapshot -- --channel ww2` uses the same collector. There is no new paid service.

The collector reads views, minutes watched, average duration and percentage, subscribers gained, traffic sources and suggested-from IDs, the full retention curve and chapter starts parsed from the published description, countries and age groups. Each optional request fails independently. `detail.json` records failed queries rather than fabricating values. `snapshots/` keeps daily raw snapshots; `board.json` supplies the studio Overview card; `READS.md` is generated.

Film reads use the first two and seven **Pacific calendar dates**, once the API reporting lag has passed. They are labelled 48h/7d for the playbook, but are not exact elapsed-hour windows. Reports retain their date ranges. A true elapsed 48-hour read requires Studio collection at that point. Comparisons use medians of the same window only. Over 1,000 impressions and under 3% CTR flags thumbnail first, then title; average percentage viewed under 25% flags the next script's opening. Collection makes no packaging changes.

## Remaining collection work

The targeted Analytics API does not expose Studio impressions/CTR, new versus returning viewers, Test & Compare, the viewer-activity heatmap or qualified Earn hours. These are **pending**, not zero. A dated Studio read can be ingested with `npx tsx scripts/field-order-studio-import.ts <read.json>`; its strict schema is exported as `studioSchema` in that file. Channel ID, read timestamp and reporting dates must match. It rejects extra fields, wrong channels and invalid dates, then rebuilds reads and the board card. `whenViewers` uses weekday 0–6 and hour 0–23, with relative activity in `viewers`; `whenViewersTimezone` must preserve Studio's displayed timezone. Partial imports merge with earlier film windows and channel reads. The importer rejects stale timestamps, unknown API windows and mismatched periods before writing.

The 06:40 job automatically dispatches the Studio-only portion through the existing unattended job queue (`field-order-dispatch.ts`). Every public long gets one job at the first run after 48 elapsed hours and one after seven days; a weekly channel job reads Earn and the viewer-activity chart. Dispatch is idempotent across every queue status and disabled until the own-channel ID and read-only token exist. A fresh own-channel snapshot is required; queue commits use the shared checkout, separate from the tracker data worktree. The workers verify Studio's selected channel, collect matching periods, import their dated results and commit the generated reports. They make no YouTube changes. This uses the studio's existing browser workers rather than a second autonomous scraper whose private UI format is untested.

Activation also needs a Studio browser signed into the new channel, with its port configured by the Chief after channel creation. No port or identity is guessed and no other channel's browser login is used. The first real read must verify the live UI's field availability; fixtures cannot establish that a new/small channel exposes demographics, viewer activity or thumbnail experiments. Suppressed fields use explicit missing reasons. Chapter checkpoints from the API are lifetime retention; Studio window metrics must not be mistaken for lifetime reach. Test results remain structured in `board.json`.

Watch-hour balances from the API are estimates for currently public longs in the trailing 365 days, not qualified YPP hours. The Earn-page value is retained separately. Seven-day forecasts require seven complete daily records, use net subscribers and public-long-only estimated hours, and stop forecasting at non-positive pace. Old hours can expire, so dates are projections rather than promises. The card preserves the 1 Feb 2027 planning line and 4,000/8,000 targets. Confirm current policy before applying: [YouTube YPP eligibility](https://support.google.com/youtube/answer/72851). The current official help still states 1,000 subscribers and 4,000 qualified public hours; the playbook's future 8,000 requirement has not been verified here from a primary announcement.

API references: [channel reports](https://developers.google.com/youtube/analytics/channel_reports), [metrics](https://developers.google.com/youtube/analytics/metrics). Demographics and retention may be suppressed with small audiences.
